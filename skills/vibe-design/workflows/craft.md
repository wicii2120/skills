# Craft

Use **Craft** for a bounded concrete artifact: design, prototype, specify, implement, redesign, polish, or produce a page, flow, component, token file, contract, reference image, design brief, or working frontend implementation.

## 1. Fix the artifact boundary

Name the artifact, users and task, target platform, evidence, settled system decisions, supplied content/assets, technical envelope, required states, responsive cases, and acceptance checks. Keep a local redesign local. Move to Systemize only when reusable architecture, ownership, governance, migration, adoption, or cross-product decisions are genuinely part of the outcome.

For supplied references, set one fidelity target:

- **Reproduce** — preserve composition and appearance; change only what responsiveness, accessibility, or feasibility requires.
- **Adapt** — preserve the visual language while changing structure for the target context.
- **Redesign** — preserve validated brand, content, and task intent while changing the solution.

A reproduction request stays reproduction unless the user changes the target.

**Gate:** The artifact, fidelity, system boundary, evidence, assumptions, and acceptance checks are explicit.

## 2. Establish direction only as needed

For visual work, load Visual Direction & Taste and state a one-line **Design Read** plus consequential choices. Ground the direction in subject, audience, task, content, brand, and platform. Use one strong direction when the brief is settled.

Load Prototyping & Variant Exploration only when direction is unresolved, the user requests alternatives, or divergent structures materially reduce decision risk. Variants differ in composition or interaction model, not merely color, radius, or copy.

**Gate:** The selected direction or exploration set has a reason rooted in context rather than habit.

## 3. Select the artifact contract

Load Deliverable Templates plus every foundation that defines a requested artifact field, then produce the smallest complete artifact that answers the request. Settled decisions remove architecture work, not the need to apply their foundation contracts. A bounded token file or component contract can be Craft when architecture is settled. Chain Systemize → Craft when architecture must first be decided.

Use real supplied content and assets. When absent, write restrained, internally consistent sample content that is visibly replaceable. Preserve factual integrity: claims, endorsements, customers, precision statistics, and real-world results require supplied evidence. Controls are semantic and functional; references never substitute fake screenshots, fake controls, hand-built placeholder icons, or unlabeled boxes for required behavior.

## 4. Handle assets deliberately

Use image generation when brand identity, illustration, photography, composition, or visual-direction risk materially benefits. It is an option, not a first-step ritual. Record each asset as supplied, generated, licensed, or provisional with rights, replacement, attribution, localization, representation, and accessibility requirements.

When visual tools are unavailable, deliver an asset brief and composition specification, identify what cannot be judged, and continue with the strongest non-image evidence path.

## 5. Implement and iterate when runnable

Load Implementation & Visual Iteration, the applicable foundations, and only the adapter matching the detected stack/tool. Preserve the portable contract while following project conventions. Complete at least one full render/inspect/refine cycle rather than stopping at code generation.

**Gate:** The artifact is complete, inspectable, and reconciled with the Design Read and contract.

## 6. Review craft and completeness

Apply the Grounding, Default, and Removal tests. Remove at least one accessory or effect that carries no meaning. Reconcile every requested file, section, and state against the `SKILL.md` completeness invariant and, for runnable work, the implementation ledger. Finish with evidence and **Now / Next / Later**.

**Completion:** The bounded artifact meets its fidelity target, system decisions, content/asset integrity, accessibility, responsive/state behavior, visual direction, and executable acceptance checks; remaining limitations are exact and tool-based rather than silently omitted.
